# Роли и права доступа

## 1. Роли

| Роль | Код (enum `Role`) | Как получить | Кратко |
|------|-------------------|--------------|--------|
| Гость | — (не авторизован) | — | смотрит публичный контент, жертвует без регистрации |
| Волонтёр / пользователь | `volunteer` | самостоятельная регистрация | выгулы, заявки на усыновление/опеку, избранное, история |
| Представитель приюта | `shelter_staff` | регистрация + заявка на приют → одобрение админом, либо приглашение от владельца приюта | ведёт анкеты, сборы, слоты, обрабатывает заявки и записи **своего** приюта |
| Администратор | `admin` | назначается вручную (сидер/консоль) | модерация, пользователи, статистика |

Уточнения:
- Роль у пользователя **одна**. Представитель приюта тоже может гулять и жертвовать
  (у него есть все возможности волонтёра) — права роли `shelter_staff` являются надмножеством `volunteer`.
- Пользователь привязан к приюту через `shelter_user` с ролью внутри приюта: `owner` (создал заявку
  на приют, управляет сотрудниками) или `staff`. В MVP у пользователя — не более одного приюта.
- Пока приют на модерации, представитель видит кабинет приюта в режиме «черновик»: может заполнять
  анкеты, но ничего не публикуется.
- Заблокированный пользователь (`is_blocked`) не может войти; его активные брони отменяются.

## 3. Как это реализуется (для этапа 6)

- `App\Enums\Role` (`volunteer`, `shelter_staff`, `admin`) + каст в `User`.
- Middleware `role:shelter_staff,admin` для групп маршрутов кабинетов.
- Policies с правилом «🔒 своё»: `PetPolicy`, `CampaignPolicy`, `WalkSlotPolicy`, `WalkBookingPolicy`,
  `AdoptionApplicationPolicy`, `ShelterPolicy`. Проверка «свой приют» — через `shelter_user`.
- `Gate::before` для админа — только для чтения и модерации, не для действий «от имени» волонтёра
  (админ не записывается на выгулы и не подаёт заявки).
- Правило «📝 после модерации»: создавать черновики можно, публиковать — только при `shelters.status = approved`.
