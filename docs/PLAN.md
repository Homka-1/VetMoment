# План разработки: сервис помощи бездомным животным и приютам

> Тема 79. Сервис помощи бездомным животным и приютам: анкеты питомцев, сбор пожертвований, запись на выгул.
>
> Рабочее название проекта сохраняем — **VetMoment** (может быть изменено на этапе 2, айдентика).
> Разработка ведётся **как с нуля**: от брифа и макетов дизайна до релиза. Существующий код
> (Laravel 13 + Tailwind 4 + PostgreSQL + Docker) используется только как техническая основа
> окружения; доменная логика «срочных запросов» удаляется и проектируется заново.

## Сквозное требование: простой запуск на Windows

Итоговый проект должен запускаться на обычном компьютере с Windows 10/11 **без ручной установки
PHP, Composer, Node.js и PostgreSQL**. Требование учитывается на каждом этапе, а проверяется на этапах 4 и 14.

**Основной способ — только Docker Desktop (одна программа):**
1. Установить Docker Desktop (WSL 2 он настраивает сам).
2. Скачать проект (git clone или ZIP с GitHub).
3. Дважды кликнуть `start.bat` (или выполнить `docker compose up -d --build`).
4. Открыть `http://localhost:8000`: база уже создана и заполнена демо-данными, демо-логины есть в README.

Что для этого нужно в проекте:
- `docker-compose.yml` по умолчанию работает в **режиме запуска**: сервисы `app` и `db` (+ `queue`),
  фронтенд-ассеты собираются внутри образа, код копируется в образ без bind-mount. Так нет медленной
  файловой системы Windows, проблем с правами и необходимости ставить Node на хост.
- Режим разработки (bind-mount + Vite HMR) вынесен в `docker-compose.dev.yml`
  (`docker compose -f docker-compose.yml -f docker-compose.dev.yml up`).
- Первый старт без ручных шагов: `start.sh` сам создаёт `.env` из `.env.example`, генерирует `APP_KEY`,
  ждёт БД, выполняет `migrate --force`, при пустой базе — `db:seed`, делает `storage:link`.
- `start.bat` / `stop.bat`: проверяют, что Docker запущен (с понятным сообщением по-русски, если нет),
  поднимают контейнеры, ждут готовности и открывают браузер.
- Окончания строк: `*.sh` всегда LF, `*.bat` — CRLF (`.gitattributes`), иначе скрипты ломаются после
  клонирования на Windows.
- Порты вынесены в переменные (`APP_PORT=8000`, `DB_PORT=5432`), порт БД наружу не пробрасывается
  в режиме запуска (нет конфликта с установленным у пользователя PostgreSQL).
- Нет зависимостей от расширений PHP и пакетов, требующих сборки под Windows.

**Запасной способ без Docker** (если виртуализация на ПК недоступна): Laravel Herd for Windows
(один установщик, включает PHP, Composer и Node) + SQLite-файл вместо PostgreSQL. Поэтому код
должен быть **независим от СУБД**: никаких pgsql-специфичных типов и функций в миграциях и запросах
(JSONB-операторы, `ILIKE`, массивы и т.п.); поиск без учёта регистра делается переносимо.
Тесты гоняются на SQLite, CI дополнительно запускает их на PostgreSQL.

## Этап 1. Бриф, роли, информационная архитектура, user flow — ✅ выполнен

Результат: [`docs/stages/stage-01-brief.md`](stages/stage-01-brief.md), артефакты в `docs/product/`.

**Цель:** зафиксировать, что именно строим, для кого и в каких сценариях.

Задачи:
1. Продуктовый бриф: проблема, целевая аудитория, ценность, метрики успеха (кол-во пристроенных
   животных, сумма сборов, кол-во выгулов).
2. Роли и права:
   - **Гость** — смотрит каталог питомцев, кампании сборов, приюты; может пожертвовать без регистрации.
   - **Волонтёр / пользователь** — записывается на выгул, оставляет заявку «хочу забрать / взять под опеку»,
     видит историю пожертвований и выгулов, избранное.
   - **Представитель приюта** — ведёт анкеты питомцев, кампании сборов, расписание слотов выгула,
     подтверждает записи и заявки.
   - **Администратор** — модерирует приюты и контент, видит общую статистику.
3. Карта сайта (IA): главная, каталог питомцев, карточка питомца, приюты, страница приюта,
   сборы, страница сбора, запись на выгул (календарь), о проекте/как помочь, вход/регистрация,
   кабинеты (волонтёр, приют, админ).
4. User flows (текстом + диаграммы Mermaid): «найти питомца → записаться на выгул», «пожертвовать
   на сбор», «приют добавляет анкету», «приют публикует слоты выгула», «заявка на усыновление».
5. Требования к данным для каждой сущности (поля анкеты питомца, поля сбора, правила слотов).
6. Нефункциональные требования: мобильный приоритет, доступность WCAG AA, русский язык, производительность.

Артефакты: `docs/product/brief.md`, `docs/product/roles.md`, `docs/product/sitemap.md`,
`docs/product/user-flows.md`, `docs/product/data-requirements.md`.

Критерий готовности: все сценарии трёх ключевых функций описаны, роли и права сведены в матрицу.

## Этап 5. Модель данных

**Цель:** схема БД под три ключевые функции.

Сущности (уточнены на этапе 1 — **источник истины: [`docs/product/data-requirements.md`](product/data-requirements.md)**):
- `users` — login, name, phone, email, role (`volunteer`, `shelter_staff`, `admin`), avatar, is_blocked.
- `shelters` — name, slug, description, address, city, phone, email, logo, walk_rules, status модерации
  (`pending`, `approved`, `rejected`, `blocked`), связь со staff-пользователями (`shelter_user`, роль `owner`/`staff`).
- `pets` — shelter_id, name, slug, species (кошка/собака/другое), sex, birth_date/возраст, size,
  breed, color, character, traits, health (прививки, стерилизация, чипирование), story, status
  (`draft`, `looking_for_home`, `on_treatment`, `reserved`, `adopted`, `archived`), `can_walk`,
  `guardianship_available`, `arrived_at`, `is_hidden`.
- `pet_photos` — pet_id, path, sort, is_cover.
- `adoption_applications` — pet_id, user_id, type (`adoption` / `guardianship`), contacts, опыт, условия, status.
- `donation_campaigns` — shelter_id, nullable pet_id, title, description, goal_amount, raised_amount,
  starts_at, ends_at, status, cover.
- `donations` — campaign_id (nullable → «в общий фонд приюта»), shelter_id, user_id (nullable),
  donor_name, amount, comment, is_anonymous, payment_status, provider, provider_payment_id.
- `campaign_reports` — отчёты о расходовании средств (текст + фото/чеки, `report_attachments`).
- `walk_slots` — shelter_id, starts_at, ends_at, capacity, booked_count, meeting_point, status;
  питомцы слота — через `walk_slot_pet`; шаблоны недели — `walk_templates` (+ `walk_template_pet`).
- `walk_bookings` — walk_slot_id, user_id, pet_id, status (`pending`, `confirmed`, `rejected`, `cancelled`,
  `completed`, `no_show`), comment, shelter_comment, cancelled_by.
- `favorites` — user_id + pet_id.
- `notifications` — стандартная таблица Laravel.

Задачи: миграции (с индексами и внешними ключами), модели с enum-кастами (PHP enums в `app/Enums`),
связи, фабрики, сидер с реалистичными русскими данными (4 приюта + 1 на модерации, 32 питомца, сборы, слоты — как на макетах этапа 3).
ER-диаграмма в Mermaid — `docs/architecture/er.md`.

## Этап 15. Демо-макет без зависимостей (запасной вариант)

**Цель:** статическая кликабельная версия сайта «на крайний случай» — если не удалось запустить ни Docker,
ни Herd. Нужна только для демонстрации: открывается **двойным кликом по `mockup/index.html`** в любом
браузере, без интернета, без сервера, без установки чего-либо.

Ограничения (обязательные):
- Только HTML + CSS + чистый JS. Никаких PHP, Node, npm, сборщиков, CDN, Google Fonts и внешних запросов —
  всё лежит в папке `mockup/` (шрифты, иконки, фото — локальными файлами).
- Работает по протоколу `file://`: не использовать `fetch`/XHR к локальным файлам, ES-модули
  (`type="module"`), Service Worker — браузеры блокируют их для `file://`. Данные — в `mockup/assets/data.js`
  как глобальная переменная (`window.DEMO_DATA = {...}`), подключается обычным `<script src>`.
- Ссылки между страницами — относительные (`pets.html`, `pet.html?id=3`), без ведущего `/`.
- Внешний вид — как у основной версии: те же токены и стили (скомпилированный CSS из `npm run build`
  копируется в `mockup/assets/app.css`, либо статическая выгрузка отрендеренных Blade-страниц).
- Работает в Chrome, Edge, Firefox на Windows; адаптив 360–1920.

Задачи:
1. Статичные страницы по карте сайта (`docs/product/sitemap.md`): главная, каталог питомцев (фильтры и поиск —
   на JS по `data.js`), карточка питомца, приюты и страница приюта, сборы и страница сбора, запись на выгул
   (календарь слотов), вход/регистрация, кабинеты волонтёра, приюта и админа (по 1–2 ключевых экрана).
2. Имитация действий: вход под демо-ролями (переключатель «Гость / Волонтёр / Приют / Админ»), «пожертвовать»
   (прогресс сбора растёт), «записаться на выгул» (место в слоте занимается), «хочу забрать» (заявка
   появляется в кабинете). Состояние — в `localStorage` с кнопкой «Сбросить демо».
3. Заметная плашка «Демо-версия: данные не сохраняются на сервере».
4. Скрипт выгрузки (опционально): artisan-команда `mockup:export`, которая рендерит страницы с демо-данными
   в `mockup/`, чтобы макет не расходился с основной версией.
5. Проверка: открыть `mockup/index.html` через `file://` в Chromium (Playwright) без сети, пройти все
   страницы, убедиться в отсутствии ошибок консоли и внешних запросов; скриншоты в `docs/screenshots/stage-15/`.
6. Раздел README «Если ничего не запускается»: открыть `mockup/index.html` двойным кликом; архив
   `mockup.zip` для отправки по почте/флешке.

Артефакты: `mockup/` (index.html и страницы, `assets/`), раздел README, `docs/stages/stage-15-mockup.md`.

Критерий готовности: на любом ПК с браузером (без интернета) после распаковки папки `mockup/` двойной клик
по `index.html` открывает работающий кликабельный демо-сайт, визуально совпадающий с основной версией.
